# Running the app with Docker

This packages the **live server-side R Shiny app** (`shiny_app/app.R`) into a container
that runs on a real R/Shiny server. (The old shinylive/WebAssembly static export is no
longer on `main`; it is archived at the git tag `shinylive-static-archive`.)

## Prerequisites

- [Docker](https://docs.docker.com/get-docker/) installed (Docker Desktop, or Docker
  Engine + Compose on Linux).
- **The data bundle `shiny_app/app_data.rds`.** It is a build artifact (~103 MB),
  **git-ignored**, and not stored in this repo — it ships to shinyapps.io via `rsconnect`
  and is regenerated by `build_app_data.R` in the upstream analysis pipeline. You must
  place a copy at `shiny_app/app_data.rds` before running the container (see below).

## Data: how the container gets `app_data.rds`

By default the image is **data-free** and the bundle is mounted at runtime, so you can
rebuild the image without the large file and swap data without rebuilding:

1. Put the real bundle at `shiny_app/app_data.rds` on the host.
2. `docker compose up --build` mounts it read-only into the container.

> If `shiny_app/app_data.rds` does not exist when you start Compose, Docker creates an
> empty **directory** at that path and the app fails to read it. Make sure the file exists first.

**Self-contained image (for deployment):** to bake the data into the image instead of
mounting it, place `shiny_app/app_data.rds` on disk, uncomment the `COPY shiny_app/app_data.rds`
line in the `Dockerfile`, and remove the `volumes:` block from `docker-compose.yml`.

## Quick start (Docker Compose)

```bash
# ensure shiny_app/app_data.rds exists first
docker compose up --build
```

Then open **http://localhost:3838**. Stop with `Ctrl+C` / `docker compose down`.

## Quick start (plain Docker)

```bash
docker build -t e2f-heart-scrna .
docker run --rm -p 3838:3838 \
  -v "$(pwd)/shiny_app/app_data.rds:/srv/shiny-app/app_data.rds:ro" \
  e2f-heart-scrna
```

Open **http://localhost:3838**.

## Figure Studio (the companion figure editor)

Every downloadable figure also has a **Figure Studio** button, which hands the built
plot to a separate app for publication styling — journal column widths in mm, per-element
fonts, per-level colours, PDF/SVG/PNG/TIFF export. That app lives in its own repo
(`figure-studio`), and its README is the contract of record for the handoff format.

The button only appears when **both** env vars are set and the directory exists:

| var | meaning |
|---|---|
| `FIGURE_STUDIO_BASE` | what the **browser** opens, e.g. `http://localhost:3939/` locally, `/figure-studio/` behind the lab nginx |
| `HANDOFF_DIR` | a directory **both containers** mount; the app writes one `<token>.rds` per click there |

Unset (plain `docker run`, rsconnect, `shiny::runApp`), the app is exactly as it was —
no button, no observers. `docker compose up --build` wires both apps together, with the
studio on **http://localhost:3939**; clone `figure-studio` beside this repo first.

Handoff files are throwaway: both apps delete anything older than 24 h, so an old link
lands on the studio's "expired" card rather than an error. The two images must carry the
**same ggplot2 version** — a figspec is a serialized ggplot object and does not survive a
version change (the studio says so plainly when it happens, but the fix is a rebuild).

## Changing the port

Map any host port to the container's `3838`, e.g. serve on `8080`:

```bash
docker run --rm -p 8080:3838 -v "$(pwd)/shiny_app/app_data.rds:/srv/shiny-app/app_data.rds:ro" e2f-heart-scrna
```

With Compose, edit the `ports:` line to `"8080:3838"`.

## What gets installed

The image (base `rocker/shiny`) adds the packages the app needs: `bslib`, `ggplot2`,
`Matrix`, `plotly`, `DT`, `svglite`, `shinycssloaders`, and **`presto`** (from GitHub —
compiled from source, so the first build takes a few minutes). `shiny`, `htmlwidgets`,
and `crosstalk` come from the base image.

## Notes

- **First build is slow** (compiles `presto` and installs packages); it's cached afterward.
- **Concurrency:** one R process serves all sessions — fine for a demo / modest launch.
  For heavier traffic run multiple replicas behind a load balancer (or ShinyProxy).
- **HTTPS / public launch:** this serves plain HTTP for local use. Before exposing it
  publicly (e.g. from the splash page), front it with an HTTPS reverse proxy
  (Caddy / Nginx / Traefik) or a platform that terminates TLS (Cloud Run, Fly.io, Render)
  forwarding to container port `3838`.
- **Feature completeness depends on the data bundle.** Tabs backed by optional slots
  (`enrich`, `score_meta`, `commun`, `refmap`) show a "run the builder" message if those
  slots are absent; run the `build_*.R` scripts against the bundle to populate them.
